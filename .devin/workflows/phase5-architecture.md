# Phase 5 — POS / Kasir Architecture

## Overview

POS is the heart of the system. Checkout is an **atomic DB transaction** — Sale, SaleItems, Inventory decrease, Movements, and Payment all succeed or rollback together.

## Workflow

```
POST /api/v1/sales/checkout
        │
        ▼
  SaleService::checkout()
        │
  DB::transaction()
        │
  ┌─────┴──────┐
  ▼            ▼
Sale         SaleItems
  │            │
  │     snapshot: product_name, sku, unit_price
  │
  ▼
InventoryService::decrease()  (per item, lockForUpdate)
  │
  ▼
InventoryMovement (type = sale)
  │
  ▼
Payment (cash / qris / card / bank_transfer)
  │
  ▼
Sale status = completed
```

If ANY step fails → ALL rollback (Sale, Items, Inventory, Movements, Payment).

## Security Rules

1. `tenant_id` — never from request, auto from Auth
2. `cashier_id` — from `Auth::id()`, never from request
3. `unit_price` — snapshot from `product.selling_price` at checkout time, frontend price ignored
4. `subtotal/discount/tax/total` — backend calculated, frontend values ignored
5. Cross-tenant product → 422
6. Cross-tenant store → 422
7. Insufficient stock → checkout fails (422)
8. Concurrent checkout → `lockForUpdate` prevents negative stock
9. Product price change after sale → sale_items snapshot preserved
10. Payment amount must cover total (or partial allowed with `payment_status = partial`)
11. Payment amount cannot exceed total + tolerance
12. `sale_number` generated by backend, unique per tenant

## Status Workflow

```
checkout → completed (default)
completed → cancelled (refund stock, reverse movement)
completed → refunded (alternative to cancelled)
```

No draft status — checkout is immediate and atomic.

## API Endpoints

```
GET    /api/v1/sales              — list (filter: status, date, store, customer)
GET    /api/v1/sales/{id}         — show (with items + payments)
POST   /api/v1/sales/checkout     — atomic checkout
POST   /api/v1/sales/{id}/cancel  — cancel + refund stock
GET    /api/v1/sales/{id}/receipt — receipt data
```

## Payment Methods (extensible for QRIS/Midtrans)

- `cash` — immediate, with change calculation
- `qris` — future: Midtrans integration via payment_reference
- `card` — future: card gateway
- `bank_transfer` — future: manual verification

Payment table is separate from Sale to support:
- Split payments (cash + QRIS)
- Multiple payment attempts
- Gateway metadata storage
- Async payment status (pending → success/failed)
