## 1. Tenant Isolation

### 1.1 New Tables
All new tables include `tenant_id` as a foreign key to `tenants` with cascade delete:

| Table | Tenant Isolation Mechanism |
|-------|---------------------------|
| `held_sales` | `BelongsToTenant` trait + FK constraint |
| `discount_presets` | `BelongsToTenant` trait + FK constraint |
| `sale_refunds` | `BelongsToTenant` trait + FK constraint |
| `sale_refund_items` | Inherits via `sale_refunds.tenant_id` |

### 1.2 Modified Tables
- `sales` — already has `tenant_id` (existing)
- `sale_items` — inherits via `sales.tenant_id` (existing)
- `payments` — already has `tenant_id` (existing)
- `stores` — already has `tenant_id` (existing)

### 1.3 Query Scoping
- All new models use `BelongsToTenant` trait → automatic `where('tenant_id', Auth::user()->tenant_id)` scope
- Explicit `withoutTenantScope()` used only in service-layer cross-tenant validation (same pattern as existing code)
- No new endpoints expose `tenant_id` in request or response

## 4. Input Validation

### 4.1 Checkout (Enhanced)

| Field | Validation | Security Purpose |
|-------|-----------|-----------------|
| `items.*.variant_id` | nullable, exists:product_variants,id | Prevent invalid variant references |
| `items.*.variant_id` | must belong to same product | Prevent variant-product mismatch |
| `items.*.variant_id` | variant must be active | Prevent inactive variant selection |
| `discount` | numeric, min 0, max subtotal | Prevent negative/excessive discount |
| `tax` | numeric, min 0 | Prevent negative tax |

**Backend-only validations (not from request):**
- `unit_price` — always resolved from backend (price list → variant → product)
- `tenant_id` — always from `Auth::user()->tenant_id`
- `cashier_id` — always from `Auth::id()`
- `sale_number` — always generated by backend

### 4.2 Hold Sale

| Field | Validation |
|-------|-----------|
| `store_id` | required, exists, belongs to tenant |
| `customer_id` | nullable, exists, belongs to tenant |
| `cart_data` | required, array, max 10KB JSON |
| `cart_data.items` | array, min 1, max 100 items |
| `cart_data.items.*.product_id` | exists, belongs to tenant |
| `cart_data.items.*.variant_id` | nullable, exists, belongs to product |
| `cart_data.items.*.quantity` | integer, min 1 |

### 4.3 Refund

| Field | Validation |
|-------|-----------|
| `type` | required, enum('full', 'partial') |
| `reason` | nullable, string, max 2000 |
| `items` | required if type='partial', array, min 1 |
| `items.*.sale_item_id` | exists, belongs to sale |
| `items.*.quantity` | integer, min 1, max original sale_item quantity |

**Backend-only validations:**
- `refund_amount` — calculated by backend, never from request
- `refunded_by` — always from `Auth::id()`
- Sale status must be 'completed' (not cancelled/refunded)
- Full refund: all items refunded
- Partial refund: sum of refund amounts cannot exceed sale total minus already refunded

### 4.4 Discount Preset

| Field | Validation |
|-------|-----------|
| `name` | required, string, max 100 |
| `type` | required, enum('percentage', 'fixed') |
| `value` | required, numeric, min 0.01; if percentage, max 100 |
| `is_active` | boolean |
| `sort_order` | integer, min 0 |

## 5. IDOR Protection

### 5.1 Held Sales
- `GET /held-sales` — scoped to `Auth::user()->tenant_id` and `store_id` query param
- `POST /held-sales/{id}/recall` — validates held sale belongs to user's tenant
- `DELETE /held-sales/{id}` — validates held sale belongs to user's tenant
- Cross-tenant access returns 404 (not 403, to prevent information leakage)

### 5.2 Refunds
- `POST /sales/{saleId}/refunds` — validates sale belongs to user's tenant
- `GET /sales/{saleId}/refunds` — scoped to user's tenant
- Cross-tenant sale access returns 404

### 5.3 Discount Presets
- All CRUD operations scoped to `Auth::user()->tenant_id`
- Cross-tenant access returns 404

## 7. Data Integrity

### 7.1 Atomic Transactions

| Operation | Transaction Scope |
|-----------|------------------|
| Checkout (enhanced) | Sale + SaleItems + Inventory decrease + Payments + Credit debit + Loyalty earn |
| Hold sale | HeldSale create only (no inventory) |
| Recall sale | HeldSale update only |
| Full refund | SaleRefund + SaleRefundItems + Inventory increase + Sale update + Payment refund |
| Partial refund | SaleRefund + SaleRefundItems + Inventory increase + Sale update + Payment update |

### 7.2 Concurrency Control
- **Checkout**: `lockForUpdate()` on inventory rows (existing pattern)
- **Refund**: `lockForUpdate()` on sale row to prevent concurrent refunds
- **Hold sale**: No locking needed (create-only operation)
- **Recall**: `lockForUpdate()` on held_sale row to prevent concurrent recall

### 7.3 Referential Integrity
- All foreign keys use `cascadeOnDelete` or `nullOnDelete` as appropriate
- `sale_refunds.sale_id` → cascade (refund deleted with sale)
- `sale_refund_items.sale_refund_id` → cascade (items deleted with refund)
- `held_sales.customer_id` → nullOnDelete (held sale preserved if customer deleted)

## 8. Sensitive Data

### 8.1 Cart Data in Held Sales
- `held_sales.cart_data` contains product IDs, quantities, and customer ID
- No payment information stored in held sales
- No personal customer data beyond customer_id reference
- Cart data is JSON, validated on write, not exposed cross-tenant

### 8.2 Receipt Settings
- `stores.receipt_settings` contains display configuration only
- No sensitive data (no payment info, no credentials)
- `logo_url` is a public URL, validated as URL format

### 8.3 Refund Reasons
- `sale_refunds.refund_reason` is free text, max 2000 chars
- Input sanitized via Laravel's input normalization (middleware trims, strips null bytes)
- No HTML rendering in backend (frontend escapes by default in React)

## 9. Threat Model

| Threat | Vector | Mitigation |
|--------|--------|-----------|
| Cross-tenant held sale access | Direct ID manipulation | Tenant scope + 404 response |
| Cross-tenant refund access | Direct sale ID manipulation | Tenant scope + 404 response |
| Refund amount manipulation | Request body tampering | Backend calculates refund_amount, never from request |
| Price manipulation | Request body tampering | Backend resolves unit_price, never from request |
| Variant-product mismatch | Sending variant_id for wrong product | Backend validates variant belongs to product |
| Refund quantity overflow | Refund qty > original qty | Backend validates qty <= sale_item.quantity |
| Concurrent refund race | Two refunds on same sale | lockForUpdate on sale row |
| Discount preset value injection | Negative or excessive value | Validation: percentage 0-100, fixed > 0 |
| Cart data injection | Oversized or malformed JSON | Max 10KB, array validation, product/variant existence |
| Feature flag bypass | Calling endpoint without feature enabled | Backend middleware enforces, frontend also checks |
